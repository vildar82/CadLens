# SDD в CAD Lens

SDD (spec-driven development) здесь означает, что наблюдаемое поведение и критерии проверки записываются до реализации. Спецификация остаётся в репозитории и обновляется вместе с изменениями. Это рабочий эксперимент, а не обещание автоматически получать правильный код из текста.

## Выбор инструмента

| Вариант | Сильная сторона | Ограничение для этого проекта |
| --- | --- | --- |
| [GitHub Spec Kit](https://github.com/github/spec-kit) | Подробный процесс Specify → Plan → Tasks → Implement → Converge, есть интеграция с Codex | Больше этапов и файлов для коротких личных экспериментов |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec) | Небольшие изменения с `proposal`, `specs`, `design`, `tasks`; есть интеграция с Codex и CLI-проверка | Дисциплину проверки поведения в AutoCAD всё равно придётся выстроить самим |
| [BMad Method](https://docs.bmad-method.org/) | Богатые роли и процессы для анализа, планирования и разработки | Для первого узкого среза это больше процесса, чем нужно |
| [Kiro](https://kiro.dev/docs/specs/) | Требования, дизайн и задачи встроены в среду разработки | Потребуется осваивать другую среду вместе с SDD |

Выбран **OpenSpec**: он позволяет попробовать полный цикл на одной небольшой функции и сохранить работу в обычных Markdown-файлах. Это выбор для старта, его можно пересмотреть после первого реализованного среза. SDD пока не единый отраслевой стандарт: у инструментов разные схемы и команды.

## Что установлено и где

OpenSpec здесь состоит из двух частей:

- **CLI** — программа `openspec` из npm-пакета `@fission-ai/openspec`. Сначала её запускали через `npx`, затем установили глобально версию 1.13.1: теперь достаточно команды `openspec`. CLI создаёт шаблоны, показывает инструкции для файлов, проверяет структуру и архивирует изменения.
- **Файлы в проекте** — результат `openspec init --tools codex --language ru`. Они хранят правила и историю работы. Это не плагин AutoCAD и не дополнительный AI-агент.

```text
.agents/skills/                         инструкции OpenSpec для Codex
  openspec-explore/SKILL.md             обсуждать идею
  openspec-propose/SKILL.md             подготовить план изменения
  openspec-update-change/SKILL.md       исправить уже созданный план
  openspec-apply-change/SKILL.md        реализовать задачи
  openspec-sync-specs/SKILL.md          перенести требования в основные спецификации
  openspec-archive-change/SKILL.md      закрыть изменение
openspec/
  config.yaml                           схема spec-driven, язык ru
  changes/                             активных изменений пока нет
  specs/                                требования завершённых изменений; пока пусто
  changes/archive/                      архив завершённых изменений; пока пуст
```

`.agents/skills/*.md` — обычные инструкции для ассистента, не исполняемый код. При инициализации CLI записал их в проект, чтобы Codex мог распознать команды вида `$openspec-propose`. В прошлой работе я прочитал соответствующую инструкцию и выполнил шаги сам: запустил CLI, написал документы, затем проверил их. Никакой скрытой генерации плана отдельным сервисом не было.

## Как пользоваться без команд

Можно просто написать: «Давай обсудим первую линзу», «Подготовь предложение по Layers» или «Реализуй согласованное изменение». Я выберу нужный процесс, запущу CLI и покажу результат. Команды полезны, когда хочется явно указать режим работы:

| Команда в чате Codex | Что она означает для меня |
| --- | --- |
| `$openspec-explore` | Обсудить идею и варианты, ничего не реализуя |
| `$openspec-propose` | Создать `proposal`, спецификации, дизайн и список задач; остановиться перед кодом |
| `$openspec-update-change` | Исправить существующий план по новым решениям |
| `$openspec-apply-change` | Реализовать задачи текущего изменения и отметить выполненные |
| `$openspec-sync-specs` | Перенести требования изменения в `openspec/specs/`, не архивируя его |
| `$openspec-archive-change` | После реализации закрыть изменение и обновить основные спецификации |

Это **команды чата**, а не команды PowerShell. Их содержимое — инструкция ассистенту, какую работу выполнить. `openspec` в терминале — другая часть системы: CLI для создания структуры, чтения статуса и проверки файлов. Команда `$openspec-apply-change` сама по себе не запускает магическую сборку: ассистент читает требования, меняет код, собирает и проверяет результат обычными инструментами.

4. Начинаем заново с обсуждения идеи в Explore. Когда договоримся о первом изменении, создадим Proposal и разберём каждый документ до реализации.

## Что такое `npx` и когда он нужен

`npx` — утилита из комплекта Node.js/npm, которая запускает npm-пакет без обязательной глобальной установки. В примере `npx --yes @fission-ai/openspec@1.13.1 validate <имя> --strict`:

- `--yes` разрешает `npx` скачать пакет при первом запуске без интерактивного вопроса;
- `@fission-ai/openspec@1.13.1` — пакет OpenSpec и версия, использованная при подготовке проекта;
- `validate <имя> --strict` — команда CLI: проверить структуру и синтаксис конкретного изменения.

Такую строку можно запускать в терминале из папки проекта. После глобальной установки тот же результат даёт короткая команда `openspec validate <имя> --strict`. Тебе запускать её необязательно: при работе над проектом это сделаю я. Она нужна как воспроизводимая ручная проверка и для будущей автоматизации. `validate` проверяет формат OpenSpec, а поведение плагина проверяют отдельно сборкой, тестами и запуском в AutoCAD.

```powershell
openspec list
openspec list --specs
# После создания изменения: openspec status --change <имя>
# После подготовки документов: openspec validate <имя> --strict
```

Глобальная установка действует на этой машине; на другой машине понадобится `npm install -g @fission-ai/openspec@1.13.1`. Для новой версии CLI её номер обновляют явно, затем обновляют проектные инструкции через `openspec update`.

## Рабочий цикл

Пустые `.gitkeep` лежат в `openspec/specs/` и `openspec/changes/archive/`: Git не сохраняет пустые каталоги, а эти заглушки сохраняют их структуру.

`CadLens.slnx` содержит виртуальные папки и явные ссылки на файлы проекта для IDE. Новые документы OpenSpec нужно добавлять в решение отдельно; реальные папки на диске при этом не меняются.

`README.md` хранит замысел проекта. Для одной функции создаётся папка `openspec/changes/<имя>/`: цель → наблюдаемое поведение → техническое решение → задачи. После просмотра плана начинается отдельный этап реализации. Код сверяется со спецификацией, а выполненное изменение архивируется; его требования попадают в `openspec/specs/`. Писать весь проект по большому ТЗ разом не требуется.
