# SDD in CAD Lens

Here, spec-driven development (SDD) means recording observable behavior and verification criteria before implementation. Specifications stay in the repository and change alongside the code. This is a working experiment, not a promise that text alone will produce correct code.

## Why OpenSpec

| Option | Strength | Limitation for this project |
| --- | --- | --- |
| [GitHub Spec Kit](https://github.com/github/spec-kit) | Detailed Specify → Plan → Tasks → Implement → Converge workflow and Codex integration | More stages and files than a short personal experiment needs |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec) | Small changes with `proposal`, `specs`, `design`, and `tasks`; Codex integration and CLI validation | We still need our own discipline for checking behavior inside AutoCAD |
| [BMad Method](https://docs.bmad-method.org/) | Extensive roles and processes for analysis, planning, and development | Too much process for the first narrow slice |
| [Kiro](https://kiro.dev/docs/specs/) | Requirements, design, and tasks integrated into the development environment | Would require learning another environment alongside SDD |

**OpenSpec** was chosen to try a complete cycle for one small feature while keeping the work in ordinary Markdown files. We can revisit the choice later. SDD is not one universal industry standard; these tools use different schemas and commands.

## What is installed

OpenSpec has two parts here:

- **CLI:** `openspec` from the npm package `@fission-ai/openspec`. It was first run through `npx`, then version 1.13.1 was installed globally. The CLI creates templates, provides file instructions, validates structure, and archives changes.
- **Project files:** generated by `openspec init --tools codex --language ru` when the project was initially set up. The artifacts and future instructions are now written in English through `openspec/config.yaml`. These files preserve the workflow and its history; they are not an AutoCAD plugin or another AI agent.

```text
.agents/skills/                         OpenSpec instructions for Codex
  openspec-explore/SKILL.md             discuss an idea
  openspec-new-change/SKILL.md          create an empty change
  openspec-continue-change/SKILL.md     create the next artifact
  openspec-update-change/SKILL.md       revise an existing plan
  openspec-apply-change/SKILL.md        implement tasks
  openspec-sync-specs/SKILL.md          copy requirements to the main specs
  openspec-archive-change/SKILL.md      close a change
  openspec-verify-change/SKILL.md       compare implementation with the plan
openspec/
  config.yaml                           spec-driven schema, English language
  specs/autocad-command/spec.md        main specification for CADLENS
  changes/archive/2026-09-19-autocad-bootstrap/  completed change
```

The `.agents/skills/*.md` files contain instructions for the assistant; they are not executable code. CAD Lens uses the step-by-step commands. The global OpenSpec profile also uses this workflow: `propose` and `ff`, which create several artifacts at once, are disabled.

## How to use it without commands

You can say, for example, "Let's discuss the first lens," "Prepare a proposal for Layers," or "Implement the agreed change." I will select the appropriate workflow, run the CLI, and show the result. Chat commands are useful when you want to specify the stage explicitly:

| Codex chat command | What it tells me to do |
| --- | --- |
| `$openspec-explore` | Discuss an idea and options without implementing it |
| `$openspec-new-change` | Create a change directory with metadata only |
| `$openspec-continue-change` | Create one next artifact, then stop for review |
| `$openspec-update-change` | Revise an existing plan after a decision changes |
| `$openspec-apply-change` | Implement the tasks and mark them complete |
| `$openspec-sync-specs` | Copy change requirements into `openspec/specs/` without archiving |
| `$openspec-archive-change` | Close an implemented change and update the main specs |
| `$openspec-verify-change` | Compare the implementation with its requirements and tasks |

These are **chat commands**, not PowerShell commands. They tell the assistant which work to perform. `openspec` in a terminal is the separate CLI for creating structures, reading status, and validating files. Running `$openspec-apply-change` does not build the project by itself; the assistant reads the requirements, changes code, builds, and tests using ordinary tools.

## What `npx` does

`npx` is part of Node.js/npm and can run an npm package without a global installation. In `npx --yes @fission-ai/openspec@1.13.1 validate <change-name> --strict`:

- `--yes` allows `npx` to download the package on first use without an interactive prompt.
- `@fission-ai/openspec@1.13.1` selects the package and the version used when the plan was prepared.
- `validate <change-name> --strict` checks the structure and syntax of one change.

Run that command from the repository root. The globally installed CLI provides the shorter equivalent `openspec validate <change-name> --strict`. You do not need to run it yourself: I will use it during project work. Validation checks the OpenSpec format; behavior is checked separately through builds, tests, and AutoCAD runs.

```powershell
openspec list
openspec list --specs
# After creating a change: openspec status --change <change-name>
# After completing its artifacts: openspec validate <change-name> --strict
```

The global installation is local to this machine. Another machine needs `npm install -g @fission-ai/openspec@1.13.1`. When updating the CLI version, do so explicitly and update the project instructions with `openspec update`.

## Workflow

Empty `.gitkeep` files preserve the `openspec/specs/` and `openspec/changes/archive/` directories in Git.

`CadLens.slnx` contains the actual project. OpenSpec files are deliberately absent from the solution file because they change frequently; browse them as folders in Rider.

`README.md` records the project idea. For each feature, create `openspec/changes/<name>/` and work through the goal, observable behavior, technical design, and tasks. Review the plan before implementation. Then compare the code with the specification and archive the completed change so its requirements become part of `openspec/specs/`. The project need not be written from one large specification at once.
